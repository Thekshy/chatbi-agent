# 安全边界设计

> ChatBI 的核心风险：LLM 生成的 SQL 直接碰生产数据。本项目把「只读边界」
> 做成纵深防御——账号权限、AST 校验、语句超时、扫描监控四层，任何一层
> 被绕过都有下一层兜底。对应 SPEC Q8 拍板与 `tests/test_tools.py` 37 条校验用例。

## 0. 威胁模型

信任边界：LLM 输出是**不可信输入**。可能出现的攻击/事故形态：

- 生成 DDL/DML（`DROP TABLE` / `UPDATE orders SET ...`）；
- 多语句拼接（`SELECT 1; DROP TABLE orders`）；
- CTE 包裹走私（`WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x`）；
- 访问系统表/跨库表（`pg_catalog` / `information_schema` 拖库）；
- 注释夹带（`SELECT 1 -- '; DROP ...`）；
- 无界查询拖垮库（`SELECT * FROM orders o JOIN order_items ...` 笛卡尔积）；
- SQL 注入工具层自身（表名/列名参数拼串）。

## 1. 第一层：只读账号（tools/run_query.py::connect_ro）

- 运行时**唯一**连接方式是 `chatbi_ro`：`GRANT USAGE ON SCHEMA public`、
  仅 `SELECT ON TABLES`（default privileges），无 CREATE/INSERT/UPDATE/DELETE；
- 读写账号 `chatbi_app` 只有 mock 生成器（`data/mock_gen.py`）持有，
  运行时代码路径里根本不 import；
- 即使 AST 校验被完全绕过，账号层仍然只读——权限是数据库给的，不是代码给的。

## 2. 第二层：AST 校验（tools/validate_sql.py::validate_sql）

sqlglot 按 PostgreSQL 方言解析成 AST，白名单外一律拒收（拒收即**不触库**）：

1. **单条只读 SELECT**：顶层只接受 SELECT/UNION/INTERSECT/EXCEPT；
   多语句（`MULTI_STATEMENT`）与 SELECT ... INTO 直接拒；
2. **全树禁写节点扫描**：`_FORBIDDEN_NODES`（INSERT/UPDATE/DELETE/MERGE/CREATE/
   DROP/ALTER/TRUNCATE/GRANT/COPY/Command/Set/Use）出现在**任何位置**都拒——
   堵住「CTE 内层藏 DML」的走私路径；`Command` 是 sqlglot 对无法识别语句
   （EXPLAIN/VACUUM/psql 元命令）的兜底形态，一并拒绝；
3. **表白名单**：`find_all(exp.Table)` 全树收集（含 CTE 内层与子查询），
   大小写折叠后必须 ⊆ {orders, order_items, products, traffic_daily, promotions}；
   CTE 别名可被外层引用，但 CTE 自身来源表仍须在白名单内；表值函数无表名，
   按白名单外处理；
4. **canonical 规范化 + 指纹**：校验通过后 AST 重输出（注释剥离、格式统一），
   SHA256 即 SQL 指纹——注释无法夹带内容，且同义重复 SQL 在执行前即被
   executor 的指纹集拦截（不触库、不耗 query 预算）；
5. **自动 LIMIT(1000)**：无则补、更大值或非字面量截到 1000（取 min）。

拒收产出机器可读码（EMPTY/PARSE_ERROR/MULTI_STATEMENT/NOT_SELECT/
TABLE_NOT_ALLOWED）+ 人话原因，直接回灌 Reflexion 修正。

## 3. 第三层：语句超时（连接级，非 SQL 文本）

`statement_timeout=5000ms` 经 libpq 连接参数 `options` 下发——自连接建立即生效，
不经过 SQL 文本（无法被生成的 SQL 关掉）。超时被 PG 侧 `QueryCanceled` 取消，
收敛为 `ok=False` 的 QueryResult 供回灌，不上抛。

## 4. 第四层：扫描行数监控（软熔断）

执行前 `EXPLAIN (FORMAT JSON)` 取计划树最大估算行数（`_max_plan_rows`），
超过 50 万记 WARN 日志（含指纹前缀）。按 SPEC Q8 拍板**不做硬熔断**：
LIMIT(1000) 与 5s 超时已构成硬约束，扫描估算只是观测点。

## 5. 工具层自身的注入防护

- `run_query` 只执行 validate_sql 产出的 canonical 片段，语句文本来自 AST 重输出
  的可信片段（无参数占位，`execute(stmt, ())`）；
- `get_schema` 的所有语句是**模块级字面 SQL 常量**，无条件分支、无动态组合；
- `get_data_profile` 的表名先过白名单，列名用字面 SQL + 参数绑定查
  information_schema 验证存在性后，才以 `psycopg.sql.Identifier`（官方安全引用，
  标识符无法走参数绑定）组合进数据查询；top_k 以 `sql.Literal` 下发，不拼串。

## 6. 预算与防失控（state.Budgets + graph 路由）

防资源失控三件套：maxSteps=6 · LLM 调用 ≤8 · run_query ≤5。预算检查在
executor 入口守卫与全部四个条件边路由函数里（超限 → reporter 输出 partial），
加上每条 SQL ≤2 次修正、replan ≤1 次、SQL 指纹去重（重复即拦截不触库）、
`recursion_limit=100` 兜底——单次分析的库访问次数与 LLM 花费都有上界。

## 7. 边界与不声称的

- Web 单用户本地、无鉴权（绑定 127.0.0.1），**不**声称生产级多租户安全；
- Docker 形态绑 0.0.0.0 仅为容器网络可达，部署者自行加防火墙/反代；
- LLM 端点（智谱开放平台）持有 key 侧的数据边界不在本项目控制面内：
  提示词会携带 schema/枚举值/示例行与数据分布摘要，不携带用户隐私明细
  （mock 库无真实用户数据）。
