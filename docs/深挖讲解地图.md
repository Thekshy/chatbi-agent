## 1. Planner（规划器）

**位置**：`src/chatbi/graph.py:321` `_make_planner_node`；解析在 `graph.py:107` `parse_plan`；
提示词 `src/chatbi/prompts.py` `PLANNER_SYSTEM`；模板目录 `src/chatbi/metrics.py:391` `catalog_text`。

被追问到这里怎么讲：

- 输入输出契约：问题 + 10 个指标模板目录（metrics.py 的 METRIC_TEMPLATES，
  每个 key 对应 SQL 模式+口径要点）+ 数据窗口/今天日期 → LLM 只输出 JSON
  `{"question_type": "drilldown", "steps": [{"description": "...", "template": "gmv"}]}`。
- 为什么 planner 不写 SQL：计划与执行分离是 Plan-Execute 的核心——步骤可审查、
  可复用（replan 只换计划不换目标），且步骤描述+模板 key 决定 executor 检索哪些表的 schema。
- `parse_plan` 的容错三连：剥 ```json 代码块 → 大括号截取 → 字段宽松匹配
  （description/desc 都认）；任何异常收敛为空计划。
- 空计划兜底（graph.py:340）：转「单步通用计划」直接拿原问题当步骤——
  因为 SPEC §4 拍板不反问、按可答部分回答。
- 步骤数截断 `steps[:max_steps]`（≤6）——规划层第一道预算。

## 2. Executor 与 text2sql（执行器 = SQL 生成现场）

**位置**：`src/chatbi/graph.py:356` `_make_executor_node`（内层 `executor_node:359`）；
SQL 提取 `graph.py:138` `extract_sql`；schema 上下文 `graph.py:242` `_schema_context`；
提示词 `prompts.py` `EXECUTOR_SYSTEM/USER`、`render_feedback`、`template_section`。

被追问到这里怎么讲：

- 一次迭代六步：预算守卫 → 取模板+检索 schema（带缓存 `state.schema_cache`，
  同表只查一次）→ 拼提示词（系统规则 + 问题/步骤 + 模板段 + 表结构段 + 反馈段）→
  LLM → `extract_sql` 提取 → 过 `validate_sql` → 指纹查重 → `run_query`。
- text2sql 的提示词工程三板斧：①指标模板给口径（GMV 三表 join、status 过滤、
  paid_at 左闭右开），②get_schema 给真实表结构+枚举值+示例行（LLM 看得到
  channel 的取值就编不出 '抖音'），③数据窗口+今天（相对时间「上个月」可换算）。
- `extract_sql` 候选优先级：```sql 块 > 整段 > SELECT/WITH 起始切片，
  **首个过校验者胜**——三候选都试，不是只解析第一个。
- 五类失败 outcome（no_sql/invalid/duplicate/error/empty）统一走内层 `_fail()`
  闭包：写 steps_log 审计 + 设 feedback + 修正机会用完则步骤标 failed。
- 成功路径 `_ok()`：证据 dict（id/sql/指纹/行数/前 5 行预览/毫秒）append 进
  evidence，`step_cursor+1`、`attempt` 归零——reporter 只认 evidence，
  「结论必有数据出处」由此保证。

## 3. validate_sql（AST 只读校验，安全核心）

**位置**：`src/chatbi/tools/validate_sql.py:92` `validate_sql`；白名单 `:26`
`TABLE_WHITELIST`；禁写节点 `:35` `_FORBIDDEN_NODES`；LIMIT 处理 `:74/:85`。

被追问到这里怎么讲：

- 五道关：空/解析失败拒 → 多语句拒（sqlglot.parse 出 >1 条）→ 顶层非
  SELECT/UNION/INTERSECT/EXCEPT 拒（含 SELECT INTO）→ **全树**扫描禁写节点
  （INSERT/UPDATE/.../Command）→ 全树收集 exp.Table 对白名单（大小写折叠，
  CTE 别名豁免但 CTE 来源表仍须白名单内）。
- 为什么全树而不是只看顶层：堵「CTE 包裹 DML」走私——
  `WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x` 顶层是 SELECT，
  但树里有 Delete 节点，照样拒。
- canonical + 指纹：AST 重输出（注释剥掉、格式统一）后 SHA256——两个好处：
  ①注释无法夹带内容；②「同义重复 SQL」（改改空白/注释/大小写）指纹相同，
  executor 查重直接拦，不触库不耗预算，逼 LLM 换路径而不是复读。
- 自动 LIMIT(1000) 取 min：无则补、更大或非字面量截到 1000——非字面量
  （`LIMIT $1`）也截，防绑定绕过。
- 拒收码（EMPTY/PARSE_ERROR/MULTI_STATEMENT/NOT_SELECT/TABLE_NOT_ALLOWED）
  机器可读，reason 人话——直接回灌 Reflexion，LLM 下一轮知道错哪了。
- 「校验本身会不会被注入」：sqlglot 是完整 SQL 解析器不是正则匹配；
  真正执行的语句是 canonical 重输出而非原文。

## 4. run_query（只读执行出口）

**位置**：`src/chatbi/tools/run_query.py:95` `run_query`；连接 `:57` `connect_ro`；
EXPLAIN 扫描 `:80` `_explain_scan_rows`；超时常量 `:33`。

被追问到这里怎么讲：

- 纵深防御第二层：入口再过一次 validate_sql（防绕过工具链直接调），
  执行的是 canonical 形态；连接一律 `chatbi_ro` 只读账号——**就算校验全被绕过，
  账号层仍然只读**，权限是数据库给的。
- statement_timeout=5s 经 libpq 连接参数 `options` 下发：自连接建立即生效、
  不经过 SQL 文本——生成的 SQL 里写 `SET statement_timeout=0` 也没用（而且
  Set 节点本来就会被校验拒）。
- 执行前 `EXPLAIN (FORMAT JSON)` 估算扫描行数，>50 万记 WARN——按 SPEC Q8
  拍板软熔断（观测不拦截），硬约束由 LIMIT+超时承担。
- 错误处理哲学：SQL 层失败（报错/超时）**不上抛**，收敛成 `ok=False` 的
  QueryResult 给 Reflexion 回灌；只有配置缺失（ToolsConfigError）向上抛——
  「SQL 错是业务问题要自愈，环境错是部署问题要暴露」。
- 每次查询独立连接（connect + with）：无状态、5s 超时不串扰，代价是毫秒级
  建连——单用户场景可接受。

## 5. reflect（Reflexion 回灌节点）

**位置**：`src/chatbi/graph.py:503` `_make_reflect_node`；画像素材 `:267` `_profile_hint`；
渲染 `prompts.py` `render_feedback`。

被追问到这里怎么讲：

- reflect 不调 LLM——它是**确定性**的回灌素材组装器：报错类反馈原样透传
  （错误原文已在 feedback.message），空集类反馈追加数据分布提示。
- 空集为什么单独处理：「查询成功但 0 行」通常是过滤值写错（`channel='抖音'`
  但库里是 live）或时间窗无数据——`_profile_hint` 解析 SQL 引用表，取优先列的
  distinct/min/max/top3 分布塞进提示词，LLM 看到 live(26000) 就知道该改什么。
- 回灌上限：每条 SQL ≤2 次修正（`Budgets.max_corrections`），路由层控制
  （`attempt-1 < max_corrections` 才进 reflect）；分布画像限 3 次
  （`_MAX_PROFILES`）防画像本身刷预算。
- 这个设计来自评测证据：全量 150 次里 42 次首轮失败、13 次自修正后
  answered 且执行正确——Reflexion 机制本身被验证有效。

## 6. 条件边与重规划（LangGraph 的「编排」所在）

**位置**：路由纯函数 `graph.py:172-212`（`route_after_planner/executor/reflect/replan`）；
装配 `graph.py:684-697` `add_conditional_edges`；replan 节点 `:520` `_make_replan_node`。

被追问到这里怎么讲：

- executor 后四分流（`route_after_executor`）：致命/预算耗尽 → reporter；
  上步成功 → 有余步回 executor / 完了去 reporter；失败且修正机会没用完 → reflect；
  用完且没 replan 过 → replan；否则 → reporter。**一张 if-else 树讲完整个编排骨架**。
- 路由是纯函数（state, budgets → 节点名）：不碰 IO、行为完全可枚举——
  tests/test_graph.py 26 条里大半在钉这些函数的每个分支。
- replan 与 reflect 的分工：reflect 修「这条 SQL 怎么写错」（局部语法/口径），
  replan 换「整个取数路径」（换模板/换维度/并拆步骤）——升级粒度不同，
  且 replan 至多一次（`state.replanned`），防无限重规划烧预算。
- replan 输入是失败摘要 `_failures_text`（最近 8 条失败步骤+原因+SQL），
  新计划为空 → 路由直接送 reporter 出 failed。
- 为什么用 LangGraph 不手写循环：条件边/状态聚合/checkpointer 开箱即用，
  且 StateGraph 本身是本项目练习目标；代价是学习成本与抽象层。

## 7. reporter 与三态落定

**位置**：`src/chatbi/graph.py:589` `_make_reporter_node`；降级模板 `:561` `_fallback_conclusion`；
状态常量 `state.py:27-29`。

被追问到这里怎么讲：

- 三态规则四行代码：致命错误或零证据 → failed；有 failed/未完成步骤 → partial；
  否则 answered。`status` 只有 reporter 可写（其余节点不碰）——**落定权集中**。
- reporter 的提示词禁令：「数值只能来自证据、引用证据用 [E1] 标号、禁止推算
  证据之外的新数值」——结论可追溯性在提示词层锁定，评测的结论正确率据此判。
- 降级路径：LLM 预算耗尽或调用失败 → `_fallback_conclusion` 规则模板
  （只陈述已有证据+未完成步骤+预算使用，**不推演新数值**）——系统在资源
  枯竭时也永远有结构化输出，不会悬死。
- 这个设计对应 EARS 验收：「预算耗尽 shall 输出 partial 含已完成部分与未完成标记」。

## 8. checkpointer（持久化）

**位置**：`graph.py:702` `run_analysis`（sqlite 连接与 SqliteSaver 在 `:721-724`）；
thread_id `:725`；图装配 `build_graph:699` `g.compile(checkpointer=...)`。

被追问到这里怎么讲：

- 用 SqliteSaver（langgraph-checkpoint-sqlite 依赖）：`run_analysis` 每次
  开一个 sqlite 连接建 saver，`graph.invoke` 带 `{"configurable": {"thread_id": ...}}`。
- thread_id 每次分析独立（uuid4）——本项目每次提问独立、无多轮，checkpointer
  的意义是**中断恢复与执行留痕**（checkpoint 表记录每步状态快照），
  不是对话记忆。
- 「为什么不用 PostgresSaver」：SPEC Q10 拍板 SqliteSaver——checkpoint 是
  运行时产物与业务库无关，放本地文件不污染 PG；且 mock 数据库按库隔离原则下
  不想再为 checkpoint 建库。注意：SPEC 里「收口 PG」指的是**数据部署形态**
  （brew 单实例按库隔离），与 checkpointer 无关，两者别混。
- 三份运行时落盘各司其职：`runs/<run_id>/trace.jsonl`（事件流，人读）/
  `runs/checkpoints.db`（图状态快照，机读）——trace 是调试与评测判读依据，
  checkpoint 是 LangGraph 的恢复机制。

## 9. 预算控制（防失控）

**位置**：契约 `src/chatbi/state.py:32` `Budgets`（6/8/5/2）；executor 入口守卫
`graph.py:364-369`；路由检查 `graph.py:181-184` 等；skipped 标记 `state.py:103`
`mark_remaining_skipped`。

被追问到这里怎么讲：

- 三件套 + 修正机会：maxSteps=6（步骤数，planner 层截断）、LLM 调用 ≤8、
  run_query ≤5、每条 SQL 修正 ≤2 次——全部集中在 frozen dataclass Budgets，
  调用点零魔数；`build_graph(budgets=...)` 可注入覆写（单测用小预算逼出 partial）。
- 检查点两处：①executor **入口守卫**（进节点先看，超限把剩余步骤标 skipped
  返回）；②**每个条件边路由**（超限一律改道 reporter）——双保险，LangGraph
  的循环结构里任何一圈都会撞上检查。
- 查重不耗预算：duplicate 拦截发生在 run_query 之前，query_calls 不加——
  「浪费 LLM 一轮可以，浪费一次库访问不行」。
- 评测验证过预算真实生效：dr006 三次采样全部 partial（两步分解题预算偏紧），
  是已知未达标归因之一——预算不是摆设，真的会咬人。

## 10. trace（可观测性）

**位置**：`src/chatbi/tracing.py:90` `TraceRecorder`；包装器 `wrap_llm:187` /
`wrap_tool:190` / `wrap_node:210`；差分采集 `observe_node:228`；收尾 `finalize:292`。

被追问到这里怎么讲：

- 事件类型六种：message（LLM 调用全文）/ tool_call / sql_result（每次生成尝试
  的判定）/ step（计划与状态变迁）/ conclusion（终态）/ usage（汇总）——逐行

  trace 数字与 api 返回的 usage 可对账。
- 评测判读直接吃 trace：纠错成功率的「首轮 SQL 失败」与 sql_result 事件
  同源同判（steps_log 差分采集）。

## 11. 横切三件（被追问概率高）

### 11a. LLM 封装（llm.py）

`LLMClient:73` / `chat:104`：参数集中（TEMPERATURE=0.2 取数任务偏确定性、

`analyze:62`：评测与 Web 共用唯一入口（测什么=用什么）；`RunConfig` 三类覆写

GET /api/schema；路由闭包引用模块级 analyze/get_schema，测试 monkeypatch 即 mock。

## 12. 评测答法（数字必须张口就来）

- **结果**：50 题 ×3 采样、题级严格多数：执行 38/50（76%❌）、结论 35/50（70%✅）、
  纠错 0/5（❌）、一致性 46/50（92%✅）。运行 2026-09-16、glm-5.3、150 次分析
  7990s、LLM 541 次 / tokens 50.7 万进 + 46.9 万出。
- **下钻层为什么只有 3/12 执行、0/12 结论**（必被追问）：四类原因——
  ①基线期歧义（5 题，「相比常规期」无唯一解，Agent 选的窗口与标注不同）；
  ②分解口径（1 题，标注要乘法分解因子，Agent 给了绝对增量）；
  ③维度覆盖（3 题，SQL 全对但结论文本只写主要维度漏了小维度——执行✓结论✗）；
  ④预算耗尽（1 题 dr006 三次全 partial）。核心教训：**下钻失败大半是
  「口径歧义题没有唯一正确答案」+「结论文本完整性」问题，不是 SQL 写不对**。
- **纠错 0/5 怎么辩护**：指标定义 = 脏题中「首轮失败但最终答对」的题。实测
  4/5 首轮直接对（无失败可纠）、1 题 1/3 恢复被多数决判否、1 题无解不进分子——
  **结构性零分而非 Reflexion 失效**；机制有效性另有全量证据（42 次首轮失败、
  13 次自愈）。v2 改进：脏题该出「必失败」陷阱（真挖好坑再考爬出来）。
- 「为什么指标不改好看点」：评测纪律——期望值唯一写入口是连库校验器、执行
  正确率靠重放不靠自报、判定是纯函数+合成数据单测钉死；未达标原样呈现留 v2。
- 「数字可信吗」：mock 库种子 20260915 可一键复现；标准 SQL 连库实测写回
  expected（50/50 校验通过）；报告 eval/reports/eval_50x3.{md,json} 入库可查。

## 13. red-team 追问速答卡

| 追问 | 一句话答 |
|---|---|
| LLM 生成 DROP TABLE 会怎样 | validate_sql 全树扫禁写节点拒收（不触库）；就算绕过，chatbi_ro 账号无写权限 |

| 为什么不用 function calling | 工具结果要进图状态（evidence/fingerprints/预算），节点函数比工具回调更可控；v1 工具就是内部函数注入 |
