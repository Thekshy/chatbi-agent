# 架构与数据流

> 本文是代码级架构说明：一次分析从问题进到结论出，途经哪些模块、哪些函数、状态如何流转。
> 面试/复盘用函数级地图见[深挖讲解地图](深挖讲解地图.md)。

## 1. 总体分层

```
┌─ 入口层 ──────────────────────────────────────────────┐
│ api.analyze()          ← 评测 runner 与 Web 共用唯一入口 │
│ ask.main()             ← CLI 调试薄壳（rich 渲染）       │
│ web/app.py             ← FastAPI 四路由 + 原生 JS 单页   │
├─ 编排层 ──────────────────────────────────────────────┤
│ graph.py               ← LangGraph StateGraph 装配与运行 │
│ state.py               ← GraphState + Budgets（预算契约）│
│ prompts.py             ← 四套提示词（planner/executor/   │
│                           replan/reporter）+ 反馈渲染    │
│ metrics.py             ← 指标模板（SQL 模式 + 口径要点）  │
├─ 工具层（只读边界四件套）──────────────────────────────┤
│ tools/validate_sql.py  ← sqlglot AST 校验 + 指纹        │

```

## 2. 一次分析的完整数据流

以「面部精华 6 月 GMV 为何环比下滑」为例，数据流按 ①→⑩ 顺序：

1. **入口**：`api.analyze(question, config)` → 包装 `graph.run_analysis()`。
   任何内部异常捕获转 `failed` 结果不向上抛（`api.py:88`）；frozen dataclass
   `AnalysisResult` 即 SPEC §7 契约（status 三态/conclusion/evidence/steps/usage/trace_dir）。
2. **装配**：`run_analysis()` 建 `TraceRecorder`（trace 开着时）→ sqlite 连接建
   `SqliteSaver` checkpointer → `build_graph()` 装配五节点图。所有依赖
   （llm/query_fn/schema_fn/profile_fn/budgets）都是可注入参数——单测注入 FakeLLM
   与工具替身，不触网不触库。
3. **planner**（`graph.py:_make_planner_node`）：问题 + 指标模板目录（`metrics.catalog_text()`）
   + 数据窗口 → LLM 输出 JSON 计划 `{"question_type", "steps":[{"description","template"}]}`。
   `parse_plan()` 做容错解析（代码块剥离/大括号截取/字段宽松匹配），解析失败兜底
   「单步通用计划」——不反问（SPEC §4 非目标）。
4. **executor**（`graph.py:_make_executor_node`）：逐步执行。每次迭代：
   - 取当前步骤的指标模板 `get_template()`，按模板涉及表调 `get_schema` 拼上下文
     （`_schema_context`，结果缓存进 `state.schema_cache`，同一表全分析只查一次）；
   - 提示词 = EXECUTOR_SYSTEM + 问题/步骤/模板段/表结构段/反馈段（`render_feedback`）；
   - LLM 回复 → `extract_sql()` 提取候选 SQL（```sql 块 > 整段 > SELECT/WITH 起始），
     首个过 `validate_sql` 者胜；
   - 五类失败分流（见下）：`no_sql` / `invalid` / `duplicate` / `error` / `empty`，
     成功则证据入 `state.evidence`、`step_cursor+1`、`attempt` 归零。
5. **reflect**（`graph.py:_make_reflect_node`）：确定性回灌，不调 LLM。
   报错类反馈原样透传（错误原文已在 feedback.message）；空集类反馈补
   `get_data_profile` 列画像（`_profile_hint`：解析 SQL 引用表 → 取优先列的
   distinct/min/max/top3 分布），让下一轮 executor 知道过滤值的真实取值域。
6. **replan**（`graph.py:_make_replan_node`）：全部步骤的修正机会用完且未 replan 过时，
   把失败摘要（`_failures_text`）回灌给 LLM 换路径重规划。至多一次（`state.replanned`）。
7. **reporter**（`graph.py:_make_reporter_node`）：汇总 evidence 生成 markdown 结论；
   三态落定规则——致命错误或零证据 → `failed`；有失败/未完成步骤 → `partial`；
   否则 `answered`。LLM 预算耗尽或调用失败时降级 `_fallback_conclusion()` 规则模板
   （只陈述已有证据，不推演新数值）。
8. **trace**（`tracing.py`）：装配期 `wrap_llm/wrap_tool/wrap_node` 包回调，
   节点函数体零改动；事件逐行 flush 写 `runs/<run_id>/trace.jsonl`，
   崩溃也保留已写事件；终态 `finalize()` 落 conclusion + usage 两条收尾事件。
9. **checkpointer**：`SqliteSaver` + 每次分析独立 `thread_id`（uuid4），
   支持中断恢复；文件在 `runs/checkpoints.db`（评测用独立的 `eval-checkpoints.db`）。
10. **返回**：`run_analysis` 返回 dict，`analyze` 转 `AnalysisResult`；Web 路由
    `to_dict()` 序列化返回，CLI 用 rich 渲染。

### executor 的五类失败 → 反馈类型

| outcome | 含义 | 反馈给 executor 的素材 |
|---|---|---|
| `no_sql` | 回复里提取不到 SQL 样式文本 | 「请只输出一条 SQL」 |
| `invalid` | 像 SQL 但过不了 AST 校验 | 拒收码 + 人话原因（`ValidationResult.reason`） |
| `duplicate` | canonical SHA256 指纹与已执行语句相同 | 已执行 SQL 列表 + 必须换路径 |
| `error` | 执行报错/超时 | PG 错误原文（回灌修正） |
| `empty` | 执行成功但 0 行 | 数据分布提示（列画像） |

修正机会 = 每条 SQL ≤2 次（`Budgets.max_corrections`）；用完 → 步骤标记 `failed`，
未 replan 过 → replan 换路径；replan 后仍失败 → reporter 出结构化失败报告。

## 3. 条件边路由（graph.py:172-212）

路由函数全部是纯函数（state + budgets → 下一节点名），单测直接钉死：

- `route_after_planner`：致命错误 → reporter，否则 executor；
- `route_after_executor`：致命/预算耗尽（LLM ≥8 或 query ≥5）→ reporter；
  上一步成功（feedback 为 None）→ 有余步继续 executor / 完成 → reporter；
  失败且修正机会未用完 → reflect；用完且未 replan → replan；否则 → reporter；
- `route_after_reflect` / `route_after_replan`：致命/预算 → reporter；
  replan 产出的新计划为空 → reporter（failed）。

递归上限 `recursion_limit=100` 由预算守卫兜底（预算先耗尽，实际到不了 100）。

## 4. 状态契约（state.py）

`GraphState`（TypedDict）四组字段：

- 计划进度：`plan`（步骤列表）/`step_cursor`/`attempt`（当前步骤尝试次数）/`feedback`；
- 预算计数：`llm_calls`/`query_calls`（steps 上限由 plan 长度约束）；
- 防失控：`fingerprints`（canonical SHA256 集）/`errors`/`fatal_error`/`replanned`；
- 产出：`evidence`/`steps_log`/`conclusion`/`status`（三态只有 reporter 可写）。

`Budgets(max_steps=6, max_llm_calls=8, max_query_calls=5, max_corrections=2)`
是 SPEC Q5/Q9 拍板值，调用点不散落魔数。

## 5. 部署形态

- 本地：brew PostgreSQL 17（按库隔离，`chatbi_app` 读写仅生成器持有 /
  `chatbi_ro` 只读运行时唯一）+ `uv run python -m chatbi.web`；
- 容器：`Dockerfile` 起同一 Web 壳（绑定 0.0.0.0:8000），PG 仍在宿主机，
  `.env` 经 `--env-file` 透传、DSN 的 127.0.0.1 换 `host.docker.internal`；
- CI（`.github/workflows/ci.yml`）：ruff + 150 条单测（`-m "not integration"`），
  不需要真实 LLM key 与本机 PG——13 条 integration 用例需要真实环境，CI 排除。
